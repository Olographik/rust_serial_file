## Overview

`rust_python_file` is a PyO3 extension that exposes a typed row file to
Python. Its example (`src/file/example.rs` and `src/file/mod.rs`) was written
against the old `rust_serial_file` file API: `FileReference::free_from_path`,
`StructFile::wrap`, buffered `reader(n)` / `writer(n)` objects, the
`Position` type, and `binary_look_up_file_struct`. That API now lives in
`rust_serial_file/src/file_old/`, which `rust_serial_file/src/lib.rs` no
longer declares, so `rust_python_file` does not compile (8 errors).

This work ports the example to the current API, `StructFile<T>` over an owned
`FileMetadata` (`rust_serial_file/doc/requirements/file/struct_file.md`), with
the serial collection traits for reading, searching, and writing. The Python
classes, methods, argument types, and return types stay the same, so the
stub generated by `stub_gen` (`python_module/rust_python_file.pyi`, a build
output ignored by git) does not change.

The binding is also tested from Python. A workspace-root script,
`test_python_module.ps1`, follows the existing `create_python_module.ps1` and
`compile_rust_lib_to_python.ps1` scripts: it builds the crate in release
mode into `rust_python_file/python_module/` (the library copied as a `.pyd`
and the generated `.pyi`), then runs the `pytest` tests in
`rust_python_file/python_tests/` against that module.

The old types map to the new API as follows:

| Old API | New API |
|---|---|
| `FileReference::free_from_path(path, 0, 0, read_only)` | `OpenOptions` (read, write and create unless read-only) + `FileMetadata::new(file, ExamplStruct::SIZE, 0)` |
| `StructFile::wrap(reference)` | `StructFile::<ExamplStruct>::new(metadata)` |
| `reader(n).read_value_at(i)` | `StructFile::read_value_at(i)` (`&self`) |
| `writer(n).write_value(&v)` | `SerialDataWriter::serial_write(v)` |
| `writer(n).write_value_at(i, &v)` (could append at `i == len`) | `serial_write_at(i, v)`, or `serial_write(v)` when `i == len` |
| `row_count()` | `SerialDataReader::serial_len()` |
| `binary_look_up_file_struct` → `SearchIndexes` → `Position` | `serial_find_by_with_context` with a `SearchContext`, whose update rule (exact, else before, else after) is the old `SearchIndexes` → `Position` rule |
| `rust_serial_file::file::position::Position` | `Option<usize>` stored directly in `PyPosition` |

## Goals and scope

### Goals

- Make `rust_python_file` compile and its tests pass against the current
  `rust_serial_file` API.
- Keep the Python-visible API identical: same classes, methods, parameter
  and return types, and the same results for the same file contents.
- Report backend errors as Python exceptions instead of panicking where the
  old code unwrapped them.

### Scope

- `rust_python_file/src/file/example.rs`: `ExamplStruct` (unchanged),
  `PyExampleFile` (ported), and its unit test (rewritten for the new API).
- `rust_python_file/src/file/mod.rs`: `PyPosition` no longer wraps the
  removed `Position` type. `make_buffer` is unchanged.
- `rust_python_file/src/lib.rs` and `src/bin/stub_gen.rs`: unchanged.
- New workspace-root script `test_python_module.ps1`, and new Python test
  file `rust_python_file/python_tests/test_example.py`.
- The existing `create_python_module.ps1` and
  `compile_rust_lib_to_python.ps1` are reused as they are, not changed.
- No change to `rust_serial_file`, `utils`, or `serialized_struct_derive`.

- Dependencies are unchanged: `rust_serial_file`, `serialized_struct_derive`,
  `utils` (path dependencies), `pyo3 0.28` with `extension-module`,
  `pyo3-stub-gen 0.22.2`; dev: `tempfile`, `anyhow`.
- `utils` is used directly for `SearchContext`
  (`utils::search::search_type::SearchContext`); it is already a dependency.

  `C:\Users\benoi\anaconda3\Scripts\python.exe`, which does not exist; the
  interpreter is at `C:\Users\benoi\anaconda3\python.exe`. Commands in this
  document set `PYO3_PYTHON` to that path for the command only, and running
  the test binary needs that directory on `PATH` so `python3*.dll` is found.
  No build configuration is changed.
- The Python tests use the same interpreter (Anaconda Python 3.13.5) with
  `pytest` 8.3.4, which is already installed there. The `.pyd` is built for
  the interpreter pyo3 was configured with, so the tests must run with that
  same interpreter. `test_python_module.ps1` takes the interpreter from
  `PYO3_PYTHON` when it is set, and from `python` on `PATH` otherwise.

  `.pyd` from the `.dll`, so they are Windows-only, like
  `create_python_module.ps1`.
- Rust edition 2024, as declared in `rust_python_file/Cargo.toml`. No MSRV.

  use it.

## Public API

Python API (unchanged, as in `python_module/rust_python_file.pyi`):

```python
class ExamplStruct:
    index: int
    def __new__(cls, index: int) -> ExamplStruct: ...

class PyExampleFile:
    def __new__(cls, file_name: str, read_only: bool) -> PyExampleFile: ...
    def read_at(self, index: int) -> Optional[ExamplStruct]: ...
    def find_by_index(self, index: int) -> PyPosition: ...
    def write(self, value: ExamplStruct) -> None: ...
    def write_at(self, position: PyPosition, value: ExamplStruct) -> None: ...
    def item_count(self) -> int: ...

class PyPosition:
    def __new__(cls, index: int) -> PyPosition: ...
    def index(self) -> int: ...

def make_buffer(len: int) -> tuple[int, int]: ...
```

Rust API of the crate (changed parts):

```rust
pub struct PyPosition(pub Option<usize>);          // was PyPosition(pub Position)

pub struct PyExampleFile {
    f: StructFile<ExamplStruct>,                    // was StructFile<ExamplStruct, Arc<File>>
    read_only: bool,
}

impl PyExampleFile {
    pub fn open(file_name: &str, read_only: bool) -> PyResult<Self>;
    pub fn read_at(&self, index: usize) -> Option<ExamplStruct>;
    pub fn find_by_index(&self, index: u64) -> PyResult<PyPosition>;   // was PyPosition
    pub fn write(&mut self, value: &ExamplStruct) -> PyResult<()>;
    pub fn write_at(&mut self, position: &PyPosition, value: &ExamplStruct) -> PyResult<()>;
    pub fn item_count(&self) -> usize;
}
```

## Errors and failure behavior

- Open errors raise `TypeError` (`RPF-EX-FR-001`); the exception type and
  message format are kept for compatibility, although `OSError` would be a
  better fit (see Out of scope).
- `read_at` maps every failure to `None` (`RPF-EX-FR-002`), as before.
- `find_by_index` now raises `TypeError` on a read error; the old code
  panicked (`unwrap`), which PyO3 turned into a `PanicException`. A failed
  comparison cannot happen: `u64` ordering is total.
- Writes raise `TypeError` for read-only files (`RPF-EX-FR-006`), I/O,
  encoding, or index errors (`RPF-EX-FR-009`). A failed write leaves the
  record count unchanged, as `StructFile` guarantees.
- No error is silently converted into a success.

## Safety and security

- No new `unsafe` code. `make_buffer` (existing, unchanged) leaks a `Vec`
  with `std::mem::forget` and hands its address to Python; it is outside
  this work (see Out of scope).
- File paths come from Python and are opened as given, as before.
- The file is not locked against other processes; `PyExampleFile` does not
  use `FileAtlas` (see Out of scope).

## Compatibility

- **Python:** no change to classes, methods, parameters, or return types;
  the stub file stays identical (`RPF-EX-RS-004`). Behavior changes, all
  toward clearer errors: `find_by_index` raises `TypeError` instead of
  panicking; writing to a read-only file raises `TypeError` with a read-only
  message instead of an OS error message; `write_at` past the end raises
  `TypeError` (the old writer's behavior there was unspecified).
- **Rust:** `PyPosition.0` changes from `Position` to `Option<usize>`, and
  `find_by_index` returns `PyResult<PyPosition>`. The old types no longer
  exist, so no Rust caller can depend on them.
- **On disk:** unchanged (`RPF-EX-DS-001`).
- `python_module/rust_python_file.pyd` and `.pyi` are git-ignored build
  outputs. `test_python_module.ps1` rebuilds them in
  `rust_python_file/python_module/`. Copying them to `python/rust/` for the
  notebook stays the job of `compile_rust_lib_to_python.ps1`.

## Performance and resource use

- Each method call uses `StructFile` directly: `read_at` is one positioned
  row read (stack buffer); `find_by_index` reads O(log n) rows; `write`
  appends one row; `item_count` does no I/O.
- The old code allocated a buffered reader or writer per call; the new code
  does not. No performance target is set.

**Planning reflection (complete before implementation):**

- *Why this breakdown:* `PyPosition` is used by `PyExampleFile`, so it is
  ported first; P-002 then restores a compiling crate. Tests come after,
  since nothing compiles before P-002. The stub check is a separate phase
  because it proves the Python API did not change.
- *Order and dependencies:* sequential; P-004 only needs P-002.
- *Risks and unknowns:*
  1. Python interpreter path (see Assumptions). If `PYO3_PYTHON` is not
     enough, the build is blocked and the user must fix the environment.
  2. Test binaries of a PyO3 `extension-module` crate need the Python DLL
     at run time on Windows; the tests call the Rust methods directly
     (no Python interpreter is started), but the DLL must still load.
  3. `find_by_index` results at the edges: the new search returns
     `before = len - 1` for a key after the last record and `after = 0` for a
     key before the first. If the old `comparator_dicotomic_search_no_context`
     returned something else at an edge, results there would differ; T-004
     pins the new behavior.
  4. `stub_gen` overwrites the `.pyi`; if it changes, the diff shows exactly
     what, and it is reverted or recorded.
- *Revision 0.2 (before implementation):* the Python tests were added at the
  user's request as P-005, after the stub check, because both need the
  release build. Coverage and Documentation, not started, were renumbered to
  P-006 and P-007. Risks: (5) `create_python_module.ps1` copies the `.dll`
  with a `Get-ChildItem -Filter target/release/*.dll` pattern; if that does
  not find the library on PowerShell 5.1, the new script fails at the
  `.pyd` step and the problem is recorded instead of changing the existing
  script without the user's approval. (6) Coverage (P-006) covers the Rust
  tests only; the Python tests run the release build, which is not
  instrumented.
